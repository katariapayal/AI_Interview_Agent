# ABTalks AI Cohort — Interview Agent

An AI agent that conducts a personalized, multi-turn technical interview based
on a candidate's actual progress through the ABTalks 31-day AI Cohort, then
produces structured feedback. Built for Problem Statement 2 of the ABTalks
hackathon.

## How it works

1. **Interview plan.** For a given candidate, the engine picks a spread of
   curriculum days from their completed missions (evenly sampled across the
   cohort timeline, not just the most recent days). If a candidate doesn't
   have enough passed missions, it tops up with skipped/failed topics framed
   conceptually. This guarantees **at least 4 days and at least 8 questions**
   (2 per day: one primary question, one adaptive follow-up) regardless of
   how the underlying LLM behaves — the counting is deterministic, the
   *content* of each question is not.
2. **Primary questions** are generated per topic, calibrated to the
   candidate's role/experience and to how they actually did on that mission
   (e.g. someone who needed 4+ attempts gets a question that probes what made
   it hard; someone who skipped a topic gets a supportive conceptual check).
3. **Follow-up questions** are generated from the candidate's actual last
   answer — pushing deeper on strong answers, asking for specifics on vague
   ones, and surfacing misconceptions without lecturing.
4. **Feedback** is generated once from the full transcript as structured
   JSON: `summary`, `strengths`, `gaps`, `next`.

Session state (conversation history, which day/question we're on) is kept
in-memory, keyed by `sessionId`, for the lifetime of the process — persistent
accounts and long-term history are out of scope per the challenge brief.

## Endpoint

```
POST /api/interview
```

Matches the Technical Specification exactly:

- **Start:** `{ "sessionId": "...", "candidate": { ...candidate.json shape } }`
  → `{ "reply": "...", "done": false }`
- **Continue:** `{ "sessionId": "...", "message": "..." }`
  → `{ "reply": "...", "done": false }`
- **Finish:** → `{ "reply": "...", "done": true, "feedback": { "summary": "", "strengths": [], "gaps": [], "next": [] } }`

No authentication required, as specified.

## Running locally

```bash
npm install
cp .env.example .env   # then fill in GEMINI_API_KEY
npm start
```

Open `http://localhost:3000` for a minimal demo chat UI (candidate picker +
live chat), or hit the API directly:

```bash
curl -X POST http://localhost:3000/api/interview \
  -H "content-type: application/json" \
  -d '{"sessionId":"demo-1","candidate": <paste one object from src/candidatesData.json>}'
```

## Testing the full loop without a UI

```bash
npm run test:cli            # uses candidate CAND-016 by default
node test/cli-interview.js CAND-003   # or pick any candidate id
```

This runs a complete interview end-to-end with canned candidate answers and
prints every turn plus the final feedback JSON — useful for sanity-checking
prompt behavior before wiring up a real frontend.

## Project structure

```
server.js                 Express app, the required /api/interview endpoint
src/interviewEngine.js    Plan selection, prompt building, turn state machine
src/llm.js                Thin Google Gemini API client
src/sessionStore.js       In-memory session map
src/curriculumData.json   Provided curriculum (copied as-is)
src/candidatesData.json   Provided candidate profiles (copied as-is)
public/                   Minimal demo chat UI (not required by the spec,
                           included so the live demo URL shows a working app)
test/cli-interview.js     End-to-end sanity check without a frontend
```

## Design notes / trade-offs

- **Deterministic pacing, dynamic content.** The *number* of questions and
  days is controlled in code so the 8-question/4-day minimum is always met
  even if the model gets chatty or terse. The *wording* of every question and
  follow-up is fully generated by the LLM from the candidate's real data and
  the conversation so far — nothing is templated or scripted.
- **Why 5 days by default, not 4.** Sampling 5 days (10 questions) gives a
  buffer above the stated minimum and a better spread across the cohort
  timeline, while staying well within a reasonable interview length.
- **Graceful degradation.** If feedback JSON parsing ever fails, the server
  still returns a valid `done: true` response instead of erroring out, so a
  single bad model completion can't fail Stage 1 eligibility.
